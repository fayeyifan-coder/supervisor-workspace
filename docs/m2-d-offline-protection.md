# M2-D 离线数据保护与独立恢复

适用于 Windows x64 本机固定 NTFS 卷。用户已明确选择方案 A，即一台由可信单用户控制的 Windows 电脑。本阶段使用合成 Profile 验收。正式 Profile 原位恢复保持 HOLD。

## 安全边界

防御误操作、选错目录、意外覆盖、程序异常退出、部分写入、损坏或不兼容的包、WAL 已提交记录遗漏、错误数据库身份和业务关联、重复切换及原始档案丢失。应用升级应继续识别已有选择记录，遇到未知格式、Schema 或损坏记录应失败关闭，原目录保留。

同一 Windows 用户权限下的主动恶意写入超出方案 A 保证范围。Windows 原生文件组件保留安全路径约束，SQLite 继续正常使用锁和 WAL。原生校验结束到 SQLite 按路径打开之间仍有交接窗口。摘要用于内容一致性，无法认证可重算清单的来源。自定义 SQLite VFS、独立 Windows 安全主体和相关原生实验暂停。

## 数据和清单

| 镜像、初始化标记 | SQLite 身份 | 关联 |
| --- | --- | --- |
| mvp.sqlite3 / mvp.initialized | 0x53574d31 / Schema 1 | 学生 UUID 是其他库的身份依据 |
| worklog.sqlite3 / worklog.initialized | 0x53574231 / Schema 1 | 工作事项和历史快照可关联学生 |
| growth.sqlite3 / growth.initialized | 0x53574331 / Schema 1 | 画像、目标、观察、历史和请求对应学生 |
| student-intake.sqlite3 / student-intake.initialized | 0x53574931 / Schema 1 | 代号、原始资料摘要、学生、计划与成长保存请求 |

格式 v1 的单个 workspace.swbackup 文件包含标识、限长 JSON 清单、按登记顺序排列的四个 SQLite 镜像，以及整包完成摘要。清单记录应用版本和 UTC 时间，并逐库记录名称、application_id、Schema 版本、Schema SHA-256、镜像字节数、SHA-256 和初始化标记。包不包含来源库的 WAL、SHM 或回滚日志。镜像包含锁取得前已提交的 WAL 记录，打开恢复库时 SQLite 创建新的侧车。每库上限 32 MiB，整个包上限 129 MiB。

备份使用应用主进程中已打开的四个连接，并按固定顺序取得 BEGIN IMMEDIATE。四把锁全部取得后复制表记录到使用可信 Schema 构建的内存库，再序列化普通 SQLite 镜像。任何锁冲突或连接状态不明都会终止。应用普通写入继续遵循各自单库事务。捕获可以保留导入部分成功状态，不能推断应用以外的跨库写入具有业务原子性。

将 feedback.sqlite3 纳入备份时需要增加已验收的 Schema 登记、关联校验、原生恢复文件清单以及新格式版本。当前 v1 对四库集合和顺序作精确检查。

## M2-A 风险复核与验证边界

| 风险 | M2-D 防护与需要观察的证据 |
| --- | --- |
| P1-1 失败清理误删目录 | 导出和恢复均没有删除或重命名目录的代码。失败保全现场。Windows 句柄按组件固定路径，禁止打开重解析点，也允许实测路径重命名被拒绝。 |
| P1-2 路径被替换成硬链接 | SQLite 快照只写入内存。文件由 Windows 组件以句柄相对的独占新建方式打开，并在同一个写句柄上完成写入、刷新和读回；已存在的名字或硬链接不会被可写打开。 |
| P1-3 验证与使用之间被替换 | 备份读取在一个受控句柄内完成。SHA-256、SQLite 完整性、跨库关联及恢复写入来自同一个内存缓冲区。恢复确认后也不会重开备份路径。导出写入的正文、完成摘要均读回检查。 |

Windows 原生组件使用 NtCreateFile 的相对单组件打开和 FILE_OPEN_REPARSE_POINT，检查实际句柄的属性，并保留祖先句柄直到操作结束。路径验证从组件打开时开始。原生文件夹选择窗口提供的是路径，无法证明从选择窗口关闭到组件打开首个句柄这段时间内，一个普通父目录没有换成另一个普通目录。即使发生这种变化，也只可能在随后检查通过的普通本地目录中排他新建，不会写入既有文件。应用返回成功之前只信任所持句柄。写入完成后，另一个同权限进程仍能修改磁盘数据或应用文件。SHA-256 可以校验内容一致性，无法证明可重写整个备份的第三方身份。请保留可信来源的备份副本。

磁盘写入和刷新失败不返回成功，可能留下未完成的包或副本。同一个目录名不会用于重试。缺少包完成摘要时校验失败。只有四库和初始化标记全部读回核对后才生成 restore.ready。普通启动继续拒绝已识别的恢复目录，新增副本的镜像位于 recovery 目录，区别于普通 Profile 的 data 目录。进程中断和短写入演练覆盖应用故障。存储设备缓存、极端资源耗尽和真实断电仍须另行验证。

## 显式激活与回退

1. 完成备份校验并生成独立副本。从工作台选择该副本的 restore.ready，核对来源时间、学生数和路径，再单独确认激活。旧实验目录继续受启动拦截，可从仍可校验的备份包重新生成新版副本。
2. 确认只登记本次会话的意图。正常关闭且四个数据库的关闭操作均成功后，写入切换请求。启动锁维持在原应用目录，原档案、恢复资料及每次生成的活动档案采用独立目录。
3. 下一次启动，先记录正在切换，再通过辅助程序重新读取副本。检查准确的目录条目、路径、单链接身份、四个初始化标记与数据库字节，重建包并核对原包 SHA-256，重复验证版本、SQLite 完整性及业务关联。文件由辅助程序从同一组受检缓冲排他写入新的活动目录。首次打开拒绝任何 WAL、SHM、journal 或未知条目。原始档案从未作为写入目标。
4. 活动副本只存在于所属工作区下。四个库全部打开且业务核对通过后，写入激活凭据，用已刷新临时文件替换状态记录，再显示工作台。正常重开允许合法的普通单链接侧车，并直接校验已打开数据库。导出包的容量限制不影响正常重开。
5. 若切换中断或校验失败，保留上一个选择和所有副本。提供经确认的回退，在下一次启动返回上一个活动档案或验证后返回原始档案。也可在面板安排返回原始档案，以后通过「选择恢复档案」选择本工作区已激活过的档案中的 restore.ready，继续使用该档案保存过的记录。两套档案不会自动合并。
6. 已初始化的切换记录缺失、损坏或版本未知时停止启动，保留现场。刷新与同目录替换用于普通进程中断恢复，管理员应保留可信备份及旧版本。将来升级如变更 Schema，先做兼容检查、备份和回退演练。正式原位恢复仍须单独设计和验收。

## 验收操作

正式使用前另行完成[合成档案升级与回退演练](m2-d-upgrade-rehearsal.md)。

1. 使用单独的合成 Profile 启动，进入「离线数据保护」。选应用数据目录之外的本机 NTFS 目录。导出会新建 sw-backup 目录。
2. 在「验证并独立恢复」选择 workspace.swbackup。确认校验结果后在 D:\Codex-Development\Temp 下生成新的 sw-m2d-restore Profile。
3. 检查普通启动仍拒绝恢复副本。从当前工作台选择并激活，再正常关闭重开。核对四库学生 UUID、工作记录、成长历史、导入绑定与待处理请求。
4. 在激活档案保存一条合成记录，关闭重开确认，重新备份并再次恢复。核对目标选择、活动目录、重复激活拦截和原始档案。返回原始档案后核对两套数据仍各自保留。
5. 分别在开发 Electron 和打包 EXE 验收。对恢复资料缺失、未知侧车和切换中断演练，确保提示明确并保全原档案。

## 历史首次 SQLite 打开 P1

原版在两次合法合成恢复中产生了相同的 15 字节完成标记，两个 M1 镜像的 SHA-256 不同。原生组件退出后，Electron 检查路径和标记，再用新的路径打开四库。合成证据用于证明完成标记未绑定恢复批次。未运行针对 SQLite 可写打开的路径替换时序。

完成记录包含包 SHA-256、原清单及原生文件身份。它记录的是生成时写入的对象。方案 A 的显式激活会重新读出四个受控输入，在可信本机环境启用一个全新活动副本。方案 B 要求的同权限写入隔离与严格句柄连续性没有得到证明。

构建 Windows x64 文件辅助程序需要系统 .NET Framework 的 64 位 C# 编译器。便携应用运行辅助程序时使用 Windows 本机 .NET Framework。Windows 打包验证将辅助程序的 PE 架构、字节以及 ASAR 中的离线保护模块纳入校验。
