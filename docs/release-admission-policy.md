# Personal Windows controlled release policy

Approved scope: current personal Windows deployment only, user instruction dated 2026-11-26. This implementation changes build/release tooling, not application business code. It is stacked on frozen candidate 3f4f1c9a74163b6a43d85da679dc834fb58a4c71; it does not merge into or change that candidate.

Ordinary Windows validation retains locked install, type check, all automated tests, production build, Windows x64 package verification and real packaged-Electron synthetic-profile smoke. It writes logs and build manifests but does not upload large application artifacts. Existing CI run 45603529635 attempt 3 remains failure due to its upload quota error. No historic status, artifact or retention setting is changed.

The separate manually dispatched candidate workflow explicitly selects a reviewed full source SHA and expected version. It records source and tooling commits separately, repeats the complete engineering gates, generates a portable ZIP with outer SHA256 and internal SHA256SUMS, then requires upload success. It creates no tag, Release or deployment. Its workflow must be available on the default branch before dispatch; merging this tooling remains a user decision. A manual run's workflow commit is not necessarily its checkout source commit; do not misrepresent it as a status on a different PR HEAD or bypass branch protection.

Local controlled builds use scripts/Build-ControlledCandidate.ps1 from a clean reviewed tooling checkout, with a clean fixed source checkout and fresh output outside the source. Node 24.19.0/npm 11.17.0 and locked Electron/builder/ASAR dependencies are required. All full validation logs, source/tooling/lock/native-compiler identities, packaged version and contents, ZIP SHA256 and internal hashes are retained. The runner performs real packaged synthetic smoke; the product-specific acceptance, backup/restore and rollback evidence must additionally match the delivered package. A successful runner is an engineering result, not deployment approval. Build tools never read formal profiles or install into formal paths.

The user permits the already completely verified local v0.2.1 ZIP as a controlled personal release input. Preserve its original source SHA, byte size and digest and existing acceptance evidence. Do not rebuild merely to change its label. A local artifact is never a CI artifact, and CI failure is never relabeled PASS. Upload quota failure alone does not block this approved local route; type/test/build/package/application failures remain blockers.

Fully disconnected cold start and a real Chinese-named Windows account remain NOT RUN, but are non-blocking for the current personal deployment by explicit user decision. Passed Chinese-directory/filename evidence remains valid. This does not promise compatibility on other accounts/computers, grant general distribution approval or authorize changing ordinary Windows network/account settings. Phase 1B remains unreplicated and is not claimed fixed.

Before formal installation: verify actual program and active profile identity; resolve drafts, active operations and pending requests; export the complete formal five-store backup and independently restore/verify it locally; retain old program and launch entry; verify candidate ZIP and manifests. Real-data access and installation/entry changes require explicit user confirmation. After upgrade verify student data and core operations, normal exit/reopen and backup. Rollback must preserve all new writes; an old backup is not a lossless substitute for the current profile. No auto-merge, auto-upgrade, deletion of backups, or formal database overwrite is authorized by this policy.
